### Blocking findings (阻塞项)

1. **“Report-only” 观察上线方案与生产 DB 约束及 Telegram 推送存在致命冲突**
   - **背景**：Spec 规定 v2 在上线前以 `report-only/dry-run` 形式验证（目标 G3），且不能直接替代 v1 控制 Telegram 推送（REQ-027）。
   - **冲突**：
     - 在 [lib/cache.py](file:///home/lin/a-stock-tracker/lib/cache.py#L68) 中，`predictions` 表的唯一约束为主键 `UNIQUE(code, framework, score_date)`。目前生产环境只启用了 Framework `A`（`SUPPORTED_FRAMEWORKS = {"A"}`）。如果在每日流水线运行时计算 v2 并写入该表，必然会覆盖 v1 写入的记录。
     - 在 [telegram_push.py](file:///home/lin/a-stock-tracker/telegram_push.py#L99) 中，Telegram 的推送逻辑直接使用 `WHERE p.entry_signal = 1` 查询，而**没有**根据 `entry_signal_version` 进行版本过滤。如果 v2 运行并写入 `entry_signal = 1`（表示 `pass_strong`，无论 Option A 还是 B 决策如何），该信号将直接被 Telegram Bot 主动推送，从而实质上替代 v1 提前上线，这违反了 "report-only" 和 "不改 Telegram 推送逻辑"（Non-goal 2）的非目标。
     - 如果不将 v2 写入 DB，则 accuracy-report（REQ-028）将无法读取 v2 的数据，导致报表无法分开展示。
   - **结论**：本 Spec 的 rollout 方案在当前 DB 主键设计和 Telegram 抓取 SQL 下无法直接落地，属于严重设计阻塞。

2. **大盘状态（market_state）注入缺乏具体的分类算法与定义**
   - **背景**：REQ-009 要求大盘状态必须由 pipeline 边界计算并作为输入传入。
   - **缺失**：
     - Spec 中仅定义了大盘状态的分类（`market_bullish` / `market_weak` / `market_unknown`），但**完全没有定义**如何判定这些状态（例如：以沪深 300 价格站上 MA60 为 bullish？还是其他波动率指标？判定所需的滚动窗口多大？判定代码的逻辑如何？）。
     - 此外，大盘指数（如沪深 300）的 Symbol 代码在不同的 API 数据源（如 Tushare 类似 `000300.SH`，BaoStock 类似 `sh.000300`）格式不同，Spec 未确定所采用的标的符号。
   - **结论**：在未定义判定公式前，Pipeline 层无法实现对大盘状态的计算与注入。

3. **现有代码库不支持前复权（QFQ）价格获取，且 Spec 缺乏数据源集成方案**
   - **背景**：REQ-005 和 REQ-006 强制要求 v2 必须使用前复权价格，且不得在不复权数据上输出 `pass_strong`。
   - **冲突**：
     - 当前代码库 [lib/akshare_provider.py](file:///home/lin/a-stock-tracker/lib/akshare_provider.py#L26) 中的 `stock_zh_a_hist` 是硬编码 `adjust=""`（即不复权）。[lib/fetcher.py](file:///home/lin/a-stock-tracker/lib/fetcher.py) 以及 pipeline 刷新逻辑目前不支持任何 QFQ 抓取参数传入。
     - 若要强制使用 QFQ，必须在 fetcher 层和数据供应层做侵入式修改，但 Spec 并没有设计如何在现有框架中支持 QFQ 数据源并行抓取，也没有说明是否在 `daily_bars` 写入时增加对 `adjusted='qfq'` 的支持（尽管 [daily_bars](file:///home/lin/a-stock-tracker/lib/cache.py#L121) 主键支持 `adjusted` 列，但上层获取与回填逻辑完全缺失）。

4. **数据模型决策待定（Option A/B/C）导致开发契约无法闭环**
   - **背景**：Spec 第 7 节将数据模型定义为“待定”，要求在实现计划中决策。
   - **冲突**：
     - 无论是 `compute_entry_signal` 还是 `EntrySignalResult` 的成员变量和类型，都取决于到底是复用原 `entry_signal` 字段扩展为多元值（Option A），还是增加新列 `entry_signal_strength`（Option B）。
     - 在决策未固定前，测试用例中的断言（如 `assert result.signal == ?`）以及 DB 写入层都无法编写。

### Important notes (关键观察/非阻塞风险)

1. **规则条件存在模糊和主观化描述**
   - REQ-013 中弱买点候选条件包含 `"MA60 slope flat/down but not severe"`。其中 `"not severe"`（不严重）是主观描述，缺乏量化标准（例如：5日累计下跌小于 1%？）。
   - REQ-013 中提到 `"none-adjusted data indicates possible trend pass"`。其中 `"possible trend pass"`（可能趋势通过）的判断条件不具体，存在二义性。
   - REQ-011 中 `high_20d_prev = max(high or close...)`。“high or close” 到底是指当日最高价 `high` 还是收盘价 `close`？在 A 股回测中这会带来显著的信号差异，需要明确指定是 `high`（突破前高）还是 `close`（收盘价突破前高）。

2. **`compute_entry_signal` 的入参及签名变化未被定义**
   - 现有的 `compute_entry_signal` 仅接收 `daily_bars`（[lib/entry_signal.py](file:///home/lin/a-stock-tracker/lib/entry_signal.py#L28)）。v2 引入了大盘状态注入和复权类型校验，但 Spec 未定义这个纯函数的新入参签名（是通过参数传入 `market_state: str` 还是在 `daily_bars` DataFrame 中作为列传入？）。

### Safety boundary assessment (安全边界评估)

- **评估结果**：**存在潜在的生产数据与推送污染风险**。
- **说明**：Spec 本身具有很强的防御性设计，声明了许多 "Never do" 非目标（不改动自动交易、不直接修改生产 cron 与 Telegram 配置）。然而，**唯一且最大的安全边界漏洞是：没有考虑到 DB 唯一索引对 Framework A 同一 score_date 的行数限制，以及 Telegram SQL 的全局扫描特性**。若直接按照 Spec 设计在生产机上“跑起来 report-only”，会导致 v2 强信号覆盖 v1 并直接推送给 Telegram 真实用户。

### Recommended next step (下一步建议)

建议拒绝当前草案并打回修改，在 Spec 中明确补充以下条款后重新评审：

1. **修正 Report-only 物理隔离方案**：
   - 方案一：修改 [telegram_push.py](file:///home/lin/a-stock-tracker/telegram_push.py) SQL 语句，使其显式过滤 `entry_signal_version = 'v1'`，从而允许 v2 在 DB 中安全写入而不触发推送（但这需要修改生产推送路径，需评估风险）。
   - 方案二（推荐）：在 `predictions` 表中利用未启用的 Framework `B`（或专门定义一个 `v2_dryrun` framework 写入数据，且此 framework 被排除在 Telegram 扫描之外），避免与 Framework A 的 v1 数据冲突。
2. **定义大盘状态公式**：
   - 给出 `market_bullish` 和 `market_weak` 的精确数学公式（如：`close > MA60` 且 `MA60` 斜率向上）。
3. **补充数据抓取（QFQ）路径**：
   - 在 Spec 中增加一节：如何修改 [lib/akshare_provider.py](file:///home/lin/a-stock-tracker/lib/akshare_provider.py) 使得 fetcher 能够并行保存 `qfq` 数据至 `daily_bars` 中。
4. **量化模糊阈值**：
   - 将 "not severe" 转化为具体的数值条件。
   - 明确 `high_20d_prev` 仅使用 `high` 列（最高价前高）或 `close` 列。
