## 2. Blocking findings (阻塞性缺陷)

### Finding 1: [BacktestConfig](file:///home/lin/a-stock-tracker/docs/plans/2026-07-08-l3-v2-offline-backtest-plan.md#L89) 数据结构与 CLI 验证命令参数不匹配
* **证据：** 
  * 在计划第二节定义了 [BacktestConfig](file:///home/lin/a-stock-tracker/docs/plans/2026-07-08-l3-v2-offline-backtest-plan.md#L89) 类，包含了 `db_path`、`start`、`end`、`output`、`artifacts_dir`、`dry_run`、`commission_bps`、`slippage_bps`、`stamp_tax_bps`。
  * 但在第三节和第四节的验证命令中，向脚本传递了 `--codes 600900`、`--no-external-fetch` 和 `--allow-tushare-fetch` 等参数。
* **风险：** 实现者如果直接照搬计划中的数据类结构和类型定义，CLI 参数解析器将无法与该数据类对齐，或者导致脚本在运行时抛出 `TypeError` 错误，迫使实现者猜测和修改类型定义。
* **最小修复：** 在 [BacktestConfig](file:///home/lin/a-stock-tracker/docs/plans/2026-07-08-l3-v2-offline-backtest-plan.md#L89) 中显式补充相关的控制字段：
  ```python
  codes: list[str] | None = None
  allow_tushare_fetch: bool = False
  ```

### Finding 2: 缺乏大盘指数的具体 Symbol 映射定义
* **证据：** 
  * 计划第四节定义了 `market_state` 基于“沪深 300”计算。
  * 但计划中没有指明该指数在数据库表 `index_prices` 中的具体 Symbol 代码。
  * 在 [cache.py](file:///home/lin/a-stock-tracker/lib/cache.py#L589) 中，系统是将沪深 300 指数的价格存储在 `index_prices` 表的 `'000300'` 键下，而不是常见的 `'000300.SH'` 或 `'sh000300'`。
* **风险：** 缺乏精确的代码符号映射会导致实现者在编写 SQLite 查询时，使用了错误的 Symbol（如 `'000300.SH'`），从而无法查到数据，使回测中的大盘状态判定恒为 `market_unknown`。
* **最小修复：** 在计划第四节中显式明确：计算大盘状态时，从 `index_prices` 中查询的 symbol 固定为 `'000300'`。

### Finding 3: 回测基本评估样本域（Base Universe）未定义
* **证据：** 
  * 计划未说明回测脚本在给定的 `--start` 与 `--end` 时间段内，是对 watchlist 中的股票进行**每日全量计算**，还是**仅对 predictions 表中历史已生成打分的股票日期**进行过滤计算。
* **风险：** L3 买点层本身是基于 L1/L2 评分的过滤层（即 `total_score >= buy_strong` 时才评估 L3）。如果对 watchlist 的所有股票在所有交易日都产生信号并统计 alpha，会混入大量 L1/L2 阶段就被拒绝的股票，导致回测结论与实盘运行环境产生根本性偏离。
* **最小修复：** 在计划中明确：回测的评估基础是以 [predictions](file:///home/lin/a-stock-tracker/lib/cache.py#L68) 表中 `framework = 'A'` 且 `score_date` 处于回测窗口内的记录为基准，在此基础上关联 [daily_bars](file:///home/lin/a-stock-tracker/lib/cache.py#L107) 进行 L3 v1 replay 和 v2 candidate 信号的派生与计算。

## 3. Important notes (非阻塞建议)

### Note 1: 临近结束日期未结案样本（NULL outcomes）的处理
* **证据：** 在回测期末（例如 2026-06-08 至 2026-07-08）新生成的信号，由于 30 天自然结案期未满，数据库 `predictions` 表中对应的 `outcome_30d` 和 `benchmark_30d` 为 `NULL`。
* **建议：** 在计算平均 Alpha、胜率（hit rate）等统计指标时，回测脚本必须显式过滤掉这部分“未结案”样本，避免在求平均值时引入零偏差（或触发 pandas 计算 NaN 异常），此逻辑应在报告模板和脚本要求中写明。

### Note 2: 实盘推送去重冷却（REQ-021A）的不一致性警示
* **证据：** 回测模型默认采用“20交易日冷却去重样本”，但目前生产环境的 [telegram_push.py](file:///home/lin/a-stock-tracker/telegram_push.py) 仍为每日日频推送（即只要条件满足就天天推送）。
* **建议：** 虽然 Spec 的 [REQ-021A](file:///home/lin/a-stock-tracker/docs/specs/2026-07-08-l3-v2-entry-signal-spec.md#L219) 规定了“未来实盘若用 v2 必须同步实现冷却”，但为防范风险，离线回测报告生成逻辑中应加入一段强提示：*“本报告中的去重胜率依赖 20d 冷却。如果实盘推送未装配冷却机制，请勿使用此去重胜率作为上线依据。”*

### Note 3: 交易摩擦模型公式与数据库单位的校对
* **证据：** 计划定义 `net_alpha_30d = raw_alpha_30d - round_trip_cost_bps / 100`。
* **说明：** 经核实，README 说明中 `outcome_*d` 和 `benchmark_*d` 以百分比存储（例如 `5.2` 表示 `5.2%`），因此 bps（基点）除以 100（即 `20 bps / 100 = 0.2%`）在数值上与 `raw_alpha` 的单位直接匹配。此公式数学正确，实现时需注意不要错误地将 `raw_alpha` 转换为 `0.052` 后再做减法。

## 4. Safety boundary assessment (安全边界评估)

* **数据库只读保证：** 计划 Phase 0 采用了 SQLite 强只读模式（`file:tracker.db?mode=ro` 结合 `PRAGMA query_only=ON`），能从数据库连接层面 100% 杜绝写入污染，此设计极为安全。
* **环境/外部接口安全：** 回测脚本明确要求“不导入 Telegram/Gemini/Sheets 模块”，能彻底隔离推送端污染风险。
* **数据获取边界：** 默认使用 `--no-external-fetch`，仅在用户显式授权且存在本地环境 token 时才允许内存中调用 Tushare 拉取 `daily` 与 `adj_factor`，未取得权限时优雅降级并打印 `QFQ_UNAVAILABLE` 诊断，外部请求边界可控。
