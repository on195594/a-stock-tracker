## 一、方向定下来：从“给老股票打分”转为“发现值得对照研究的同业公司”

**产品方向：以原观察池中的非金融公司为出发点，找出同业中盈利能力与估值值得比较的公司，帮助本人决定下一家研究谁，并看清后续变化。**

不是恢复 Framework A，不是重新开发行情软件，也不是先建设一个量化研究平台。本轮暂不解决买点、仓位、卖点或收益证明。

日常使用场景固定为：

> 我正在研究一家已关注的公司。运行一次工具，看到同业候选、它们与这家公司的指标差异、数据缺口，以及下一步要核查的问题。下次运行，看到事实和候选发生了什么变化。

本轮主线只有三次交付：

| 顺序 | 交付结果 | 回答的问题 |
|---|---|---|
| 1．同业发现 | 一家参照公司＋实际池外同业＋ROE/PB 比较表 | 除了原来关注的公司，还有谁值得看？ |
| 2．候选审查 | 前三名的事实、与参照公司的差异、待核查事项 | 它为什么排在前面，我该查什么？ |
| 3．变化跟踪 | 两次报告的候选变化与原始指标变化 | 哪家公司需要重新看一眼，原因是什么？ |

**原 35 股只用于接入验证、选择参照公司和标记“旧池／池外”。池外发现是第一次产品交付的必需能力，不再写成“以后需要时再扩池”。**池外股票进入比较，不等于它必须胜出；没有更好的候选，也是一种合法结果。

### 工具放在哪里

现行 `AGENTS.md` 明确要求 Framework A 保持结案，并将本文及配套 Spec 列为已授权的新方向。[R1]

本路线采用明确边界：**正式文档保存在 tracker；tracker 继续维护通用数据；新功能在它旁边的独立工作目录 `a-stock-screen/` 中作为一个个人脚本实现。**独立的是实现和写入位置，不是另起一套治理或部署架构。该目录是独立 Git 仓库，只管理本工具源码；公开远端为 [`on195594/a-stock-screen`](https://github.com/on195594/a-stock-screen)，不创建新服务或数据库。

默认使用 tracker 已有 Python 环境和可公开调用的共享库能力；不通过导入旧 CLI 来获得初始化、网络或写库副作用。不修改旧评分、manifest、预测表、研究报告和 cron。当前实现位于独立目录；本文不授权任何生产修改。

## 二、现有项目到底复用什么

| 现有位置 | 实际用途 | 本轮处理 |
|---|---|---|
| `a_stock_tracker/config.py::WATCHLIST` | 硬编码 35 股，混有金融与非金融，条目没有行业字段 [R2] | 只作为原关注集合和参照公司来源；不扩写此常量 |
| `tracker.db::stock_fundamentals` | 表中有 `industry`，JSON 中有基本面和估值 [R3] | 用显式只读连接读取；不要仅从 WATCHLIST 取行业 |

| `tushare_primary_materialization.py` | 已计算 ROE、PB 等；其中均值函数会跳过缺失值 [R4] | 借用已确认的字段含义，不盲信名称为“三年均值”的值必有三个有效年度 |
| 已有 TuShare 连接和依赖 | 数据访问能力；2026-09-22 已验证本次所需接口权限 | 只补本工具必需的基础信息、当日估值、最近年报 |
| `scoring.py`、`weights.json`、旧评估器 | 已结案实验的评分和评估口径 | 不修改、不复活、不作为新筛选入口 |
| QFQ、L3、Telegram 相关代码 | 旧数据或研究能力 | 不接入本轮主链；没有当前需求就不动 |

这里最重要的边界是：**复用已有事实和连接，不复用旧实验的结论，也不为了新功能翻修旧采集链。**

## 三、第一次交付：真正生成池外同业比较表

### 3.1 输入与股票范围

输入一个原池中的非金融股票代码，称为“参照公司”。金融或行业不明的输入明确提示不适用，不临时套用同一公式。

默认只处理该公司的一个提供方行业标签；使用 `stock_basic` 的明确行业、交易所、市场和上市状态字段匹配当前沪深主板同业。[E1] 这是粗粒度同业研究，不意味着主营业务完全可比。不要读取几家公司名称后自行猜行业。

**范围上限：参照公司＋至多 49 家同业。**先保留参照公司，再从有同日估值及有效总市值的其他同业中按总市值降序取 49 家；同值按代码。少于 49 家就全部处理。之后因财务不完整而被排除的对象不再由后续名次补入。

这个上限只控制逐股财务读取量；按市值取样会偏向较大公司，报告必须说明，不称为完整行业或全 A 股扫描。同次 `stock_basic` 返回的当前名称去空白并转大写后，以 `ST` 或 `*ST` 开头即视为已知风险警示，不进入候选；名称缺失或未做其他完整风险核验的对象标“风险状态待核查”，不把有当日 PB 当成可交易证明。

### 3.2 数据只补三类，不建全市场数据工程

| 数据 | 优先读取 | 不足时的最小补法 |
|---|---|---|
| 代码、名称、行业、市场与上市状态 | 已有、日期明确的基础信息 | `stock_basic`；仅用于确定本次同业范围 |
| 同一交易日的 PB、总市值 | 已有当日估值记录 | `daily_basic`；按同一个明确数据日读取 |
| 连续三个年度的 `roe_waa`、报告期、公告日期 | 原始财务记录；不是只有均值的二手字段 | 对入围同业逐股读 `fina_indicator`，只取需要的近年数据 |

这些字段和查询方式来自 TuShare 官方接口文档；普通财务指标接口是逐股查询，不能假定自己拥有全市场财务批量权限。[E1]、[E2]、[E3] 同业范围先缩小，再读取财务，避免给全市场逐股补三年数据。

每种字段使用明确来源；来源发生变化就记录到快照，不逐字段偷偷拼不同日期。接口达到返回上限时补取所需范围或报缺口，不把截断的第一页当全集。权限错误直接列明缺哪个接口，不切换多个供应商，不自动购买权限。

旧库读取与新增请求的规范化结果保存在本次 `snapshot.json`。后续可直接读此文件，不要求新缓存数据库、批次仓库或后台任务。原库只能读；在线补数必须由 `--refresh` 显式触发。

### 3.3 筛选规则一次写清楚

本轮唯一规则名为 `peer-screen-v1`，用于安排研究优先级，不是买入建议或已验证收益模型。

**输入资格：**行业适用；PB 为同一数据日的有限正数；有三个连续年度、每年一个明确可用的年报 `roe_waa`。三个季度不算三年，只有两个非空年度的均值也不算；空值、布尔值、NaN 和无穷均不能当正常指标。同一年度先去除精确重复行；有且仅有一条 `update_flag=1` 的修订记录时采用该记录，没有修订记录且只有一条原始记录时采用原始记录，其余多版本冲突单列并排除。快照记录所选 `update_flag` 和选择依据。公告期晚于本次实际运行时间、来源不明的行单列。旧数据只能展示，不能通过改运行日期成为新数据。

ROE 采用最近已披露的连续三年均值，逐年数值和年度同时展示；最新年度差异注明，不掩盖年报更新错位。最新年度期末距数据日超过 550 个自然日时不参与排序，防止久未更新的数据混入；这只是首版运行上限，不是投资参数。新取得的修订值只用于当前研究，不倒称历史时点已经知道。

**候选范围：**三年 ROE 均值大于零、PB 大于零且通过以上输入检查。负 ROE 公司留在排除表，避免把一个整体盈利不佳的小组也机械称为“优质候选”。这一正均值限制是本次新增的明确初值，不是收益优化结果。

**同业内部排序：**

```text
ROE 名次：三年均值从高到低，越高越靠前
PB 名次：同日 PB 从低到高，越低越靠前
研究次序 = (ROE 名次 + PB 名次) / 2
```

并列特征采用平均名次，最终同值按股票代码；不使用展示舍入值决定名次。只展示同业前三作为优先核查对象，并单列参照公司的实际位置。合格数不足三只则展示实际数量；只有一只时称“事实展示”，不称筛选胜出。不建立跨行业总榜。

高 ROE、低 PB 只是一个可以解释的筛选起点，不能证明经营质量、风险低或低估。本人仍需核查杠杆、净资产变化、一次性损益和主营业务差异。第一轮不增加成长、技术、情绪、护城河等新分数，也不调权重。

### 3.4 开发顺序与修改位置

在新目录的 `screen.py` 中先写普通函数，不为以下职责分别建服务、工厂或配置框架：

| 顺序 | 要写的功能 | 直接检查什么 |
|---|---|---|
| 1 | `load_reference()`：读取原关注集合、参照股与旧缓存 | 按路径用 `ast.literal_eval` 读取 WATCHLIST 字面量，不执行旧模块；行业取表字段/基础信息，旧库 `mode=ro`，不调用 `get_db()` |
| 2 | `load_peers()`：枚举同业，按上述市值规则截取 | 能处理原 35 股以外的证券；未扩写旧 WATCHLIST |
| 3 | `load_inputs()`：取得同日 PB 和三个年度 ROE | 展示各年值、日期、来源及排除原因；不把缺失补零 |
| 4 | `rank_peers()`：纯计算名次和相对位置 | 小样本手算一致；相同快照结果一致 |
| 5 | `render_report()`：先输出最小比较表 | 报告里出现池外同业的真实数据与旧股位置 |

读取旧 35 股跑通可以是第 1 步的调试手段，但不能把它单独当“选股能力已交付”。不规定要拆多少 PR，也不先花一轮整理旧目录。

### 3.5 报告长什么样

```text
参照公司：本人输入的公司
范围：该公司所属行业；有估值的同业按市值截取；非全市场
数据：PB 日期；年报年份；生成时间
覆盖：枚举数 / 本次处理数 / 合格数 / 缺失数

公司 | 旧池/池外 | 三年逐年ROE | ROE均值 | PB | 研究次序 | 待核查
同业前三……
参照公司（若未入前三，仍单列；若不合格，显示原因）……

未入选和数据缺口……
```

**完成标志：**真实数据中至少一家公司来自原 35 股之外，完成同口径比较；能说明参照公司处于什么位置。若池外对象都不合格，交付缺口而非虚假候选，该次只算接入成功，尚未验证发现能力。不能为了凑出“新发现”放宽规则。

## 四、第二次交付：让前三名能指导下一步核查

不增加新接口或模型。直接用第一次交付已有数据，为前三名各生成一个短段落：

| 内容 | 实现方式 |
|---|---|
| 为什么排在前面 | 显示 ROE、PB 各自名次与综合次序，而不是重复“高分” |
| 与参照公司比怎样 | ROE 均值差多少个百分点；PB 高/低多少倍。年报覆盖不同则注明；参照公司不合格时不伪造比较 |
| 哪些已知事实值得警惕 | 逐年 ROE 中出现负数、最新年度 ROE 下降、报告期明显错位等；只描述实际数据 |
| 还需要查什么 | 固定的待核查问题：主营业务可比吗？高 ROE 是否靠杠杆/一次性收益？低 PB 是否反映资产质量问题？风险警示和可交易性如何？ |

“PB 更低”不写成“被低估”；“ROE 更高”不写成“未来回报更高”。不能把固定问题伪装成已发现的负面事实。

**完成标志：**本人读完后，对至少一家公司作出“继续研究／暂不研究”的实际判断，理由写进原有笔记即可。无需开发日志录入、打分或审批工具，也不强求判断必须是正面。

做到这里已经是一项可保留的个人工具：它同时具备池外发现、同业比较和核查指引。不要为了第三次交付而推迟使用。

## 五、第三次交付：下一次运行时，只突出值得重看的变化

增加一个函数 `compare_snapshots()`，读取本人指定的上一份快照，与本次结果比较，不建立 latest 指针或新表。

只输出四种变化：新进入前三、退出前三、PB 数值变化、逐年 ROE/采用年报发生变化。每个变化尽可能关联原始字段，不只说“排名升了”。

必须区分：**公司数据变了**、**同业成员变了**、**规则变了**、**这次数据没取到**。后两种不能写成公司变差；成员改变时不直接把名次变化归因于公司本身。PB 数值变化也不能未经核查就归因于股价变动。

相同输入不重复制造“新发现”。首次运行无上期结果就省略变化栏。完整排名可放报告后面，阅读顺序改为“变化 → 本次前三 → 参照公司 → 缺口”。

**完成标志：**两次真实运行可对照；本人不必重读整张列表，就能决定是否需要重看某家公司。自动 cron、Telegram 和价格告警不属于本次交付。

## 六、实现保持这么小

### 6.1 文件和命令

```text
a-stock-tracker/              既有项目，不改旧实验
└── .venv/                    尽量复用既有依赖环境

a-stock-screen/               独立 Git 仓库，不是新平台
├── AGENTS.md                 本工具边界与验证要求
├── README.md                 使用入口和当前状态
├── .gitignore                忽略输出、凭据和本地缓存
├── screen.py                 读取、调用提供方、排序、渲染和简单比较
├── test_screen.py            与本工具直接相关的少量测试
└── output/<运行时间>/
    ├── snapshot.json         本次实际输入、范围、规则及结果
    └── report.md             给本人看的报告
```

`output/`、凭据和本地缓存已由 `.gitignore` 排除；旧数据库和供应商凭据不复制到新目录。

以下前两个命令已经可用；`--compare` 仍属于第三次交付。从 `a-stock-screen/` 运行；示例代码来自旧池，仅演示语法，不是选股推荐：

```bash
# 第一次：只读旧库，显式联网补充同业输入，输出一次报告
../a-stock-tracker/.venv/bin/python screen.py \
  --tracker-root ../a-stock-tracker --anchor 600900.SH --refresh

# 复看：完全使用已保存的数据，不联网
../a-stock-tracker/.venv/bin/python screen.py \
  --input output/<上次运行>/snapshot.json

# 第三次交付才增加：生成当前结果，并与指定旧结果对照
../a-stock-tracker/.venv/bin/python screen.py \
  --tracker-root ../a-stock-tracker --anchor 600900.SH --refresh \
  --compare output/<上次运行>/snapshot.json
```

只有 `--refresh` 允许联网，默认读取快照或已取得的数据。缺少基础信息时明确提示缺口，不隐式切换成在线任务。没有可用的已完成交易日信息时，可显式传 `--date YYYY-MM-DD`；报告按真实取得的 PB 日期展示，不将数据日冒充历史决策时刻。本工具不提供历史时点回测。

每次输出独立目录，不覆盖旧结果。快照保存参照公司、同业范围、处理上限、原关注集合、逐年 ROE、PB 日期与来源、排除原因、规则名和结果。重放时规则必须匹配；不支持的旧规则保留原结果供查看，不套用当前规则冒充原次结果。字段不足的旧快照可以显示事实，但不编造逐年 ROE 通过新规则。

### 6.2 真正需要的测试

只围绕三个容易出错的点写测试：三年数值与日期正确；排序、并列及范围截取可复现；新命令不写旧库、离线模式不联网且不覆盖旧输出。变化功能再补一例“成员变化不是公司恶化”。测试使用临时库/fixture，不访问真实生产数据。

新工具用自己的少量测试验证。若确实修改 tracker 的现有代码，再执行该仓库已有完整检查；不得因为文件放在外面就顺手改旧代码而不验证。不以新增测试数量或代码行数验收。

### 6.3 卡住时怎么推进

| 真正的卡点 | 下一步只做什么 | 不做什么 |
|---|---|---|
| 旧均值无法证明来自三个年度 | 读取原始年报；拿不到就列出缺失公司 | 重构全部财务物化器 |
| 新同业的财务接口无权限 | 使用一份有来源、同字段的本人导出 JSON；无数据则明确不能完成同业发现 | 接入多个供应商或建设权限平台 |
| 行业太大、逐股请求太多 | 执行既定市值截取，不增加处理上限；披露范围偏差 | 抓全市场所有财务历史 |
| 候选看起来不对 | 先核对三年口径、PB 日期及主营业务可比性；记录一个具体反例 | 同时加多个因子或调权重 |
| 已经使用三次仍没有价值 | 根据真实反例只改一次规则/呈现；仍无帮助就停止新增功能 | 自动转入回测、AI 或平台建设 |

## 七、本轮收口与后续方向

### 当前正式安排

早期修订草案中的数据库、批次、实验注册、发布治理和预算闸门不恢复。只读旧库、普通快照和少量测试保留；**“只排旧池即可”“池外扩展可选”“所有新功能放回旧仓库”“一律不联网”均不是当前实施安排**。新工具独立放置，第一次交付即有同业发现，只有显式刷新可以联网。新规则要求正 ROE 均值并核实逐年数值，旧结果不重写。

### 什么时候停止本轮开发

同业池外数据能比较、本人能作出一次实际核查决定、下次能看见事实变化，就停止新增功能。若前两次交付已经足够使用，也可以先停在第二次。不要把第三次交付当作继续堆功能的开端。

后续投入只允许由真实问题触发：

- 只有某一行业的指标明显不适用时，才另做该行业的简单比较；不同时开发六套框架。
- 只有反复手工刷新已经造成负担时，才为新工具增加一个低频任务；不恢复旧 daily。
- 只有本人已持续使用，并明确要回答“这个排序是否有投资增量”时，才另立有样本、截止日和样本外验证的新研究；当前快照不自动变成无偏回测数据，也不设“等待收益成熟才能继续用工具”的条件。

**第一次交付已完成，第二次功能已实现：**相邻 `a-stock-screen/` 中的独立 `screen.py` 已用长江电力作参照完成真实运行，枚举 22 家水力发电主板公司、17 家合格、其中 16 家来自旧池外；报告已为前三名生成排序原因、参照差值、已知事实和固定核查问题。原库只读，旧实验未动。下一步由本人阅读报告并作出一次“继续研究／暂不研究”判断；完成该验收前不继续第三次交付。
