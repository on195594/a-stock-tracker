# Cron and Reviewer Reliability Fix

Date: 2026-07-23
Status: approved for implementation
Owner: Hermes PM

## 1. Goal

Close three bounded reliability gaps without changing scoring, Telegram message content, databases, schedules, dependencies, or external API contracts:

1. make `cron-alert-wrap.sh` accept its optional label and `--alert-exit-2` in either order while preserving the current canonical invocation;
2. make `cron-setup.sh` recognize and replace active, project-local semantic variants of the daily pipeline command, so HOLD readiness preserves an existing daily lane and repeated installation leaves exactly one managed daily rule;
3. retry direct and `urllib.error.URLError`-wrapped timeouts in `agent_reviewer` using the existing bounded retry budget.

## 2. Current evidence

- The previously reported claim that the current acceptance cron passes `--alert-exit-2` in the label slot is false. Source and live crontab currently pass command, label, then option; existing execution tests prove exit 2 emits `ROLLBACK`.
- The wrapper parser is positional, so a future manual invocation with option before label is rejected or misinterpreted.
- `PRESERVE_EXISTING_DAILY` only searches for the exact substring `pipeline.py daily`; cleanup similarly relies on narrow text fragments.
- Direct `socket.timeout` and `URLError(socket.timeout)` both currently make one call and immediately return fallback. Official Python documentation states that `urlopen()` raises `URLError` for protocol errors and that `URLError.reason` may be another exception.

## 3. Requirements

### REQ-001 — Wrapper option parsing

- The first argument remains the complete command.
- At most one human-readable label and one `--alert-exit-2` option may follow, in either order.
- The current canonical order remains generated by `cron-setup.sh`.
- Unknown options, duplicate labels, or duplicate `--alert-exit-2` return exit 64 before running the wrapped command.
- Default exit-2 suppression and nonzero exit-code passthrough remain unchanged.

### REQ-002 — Daily semantic detection and cleanup

- Only active, project-local crontab lines may qualify as an existing daily job; comments and another project's `pipeline.py daily` must not qualify.
- Recognize at least these equivalent project-local forms:
  - `python pipeline.py daily` with path/spacing variants;
  - `python -m pipeline daily`;
  - the canonical `cron-alert-wrap.sh "... pipeline.py daily" daily` form.
- On HOLD readiness, an existing recognized daily lane preserves installation of daily, acceptance, and outcome rules.
- Legacy recognized project-local daily variants are removed before the canonical managed block is generated.
- Re-running setup is idempotent: exactly one canonical managed daily rule remains, and unrelated crontab entries remain byte-for-byte unchanged.
- `PROJECT_DIR` is canonicalized to its physical path before matching and generation.

### REQ-003 — Reviewer timeout retry

- Direct `TimeoutError`/`socket.timeout` is retryable.
- `urllib.error.URLError` is retryable only when its `reason` is a `TimeoutError`/`socket.timeout`.
- Retry uses existing `MAX_RETRIES=3` and `RETRY_DELAYS=(2, 4)`; no new dependency or unbounded retry.
- A success on the third attempt returns a non-fallback `ReviewOutput`.
- Exhausted timeouts return fallback after exactly three attempts.
- Non-timeout `URLError`, HTTP 401/403, and parse/validation errors remain immediate fallback.
- Tests patch `urlopen`, `sleep`, curl, crontab, environment, and filesystem; no real network, credential, or production DB access.

## 4. Non-goals

- Telegram `_send` retry or message-length changes.
- Cron schedule changes, new jobs, readiness policy changes, or shell replacement.
- Gemini model, prompt, timeout duration, payload, authentication, or response schema changes.
- Database reads/writes or schema changes.
- New dependencies or `.env` changes.
- Broad refactoring of `agent_reviewer` or cron generation.

## 6. Production landing

1. Commit the verified isolated branch and cherry-pick it onto `agent/qualitative-v2-shadow` only if the production worktree is clean.
2. Save `crontab -l` to a timestamped backup before running `cron-setup.sh`.
3. Run the production installer once. It creates its own second rollback snapshot.
4. Compare before/after crontab:
   - unrelated entries unchanged;
   - managed schedules unchanged;
   - one acceptance rule with canonical third-argument `--alert-exit-2`;
   - one canonical daily rule.
5. Run fake-curl wrapper smoke only; do not send a real alert or call Gemini.

## 7. Rollback

- Code: `git revert <production-commit>`.
- Crontab: `./cron-setup.sh --rollback <pre-change-crontab-snapshot>` or `crontab <snapshot>`.
- If installer output removes daily/acceptance/outcome unexpectedly, changes unrelated entries, or readiness state cannot be interpreted, restore the snapshot immediately and stop.

## 8. Stop conditions

Stop automatic progress if any of the following occurs:

- scope expands to Telegram retry, DB, credentials, schedule changes, or new dependencies;
- tests require real network or production data;
- fake-crontab output and live installer behavior diverge;
- unrelated crontab entries change;
- deterministic verification and independent review disagree on a core requirement;
- the production worktree is dirty or a relevant job is running during installation.
